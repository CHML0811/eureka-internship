What This Project Builds

One sentence: a smart document reader that figures out what kind of document it's looking at, sends it to the right tool, and returns clean data the graph database can use.

Step 1
📥 Document comes in
Could be a passport scan, an org chart, an annual report — anything.
↓
Step 2 — Classifier
🔍 What type is this?
Labels it: form, chart, hybrid report, ID document, or hand-drawn diagram.
This is like the receptionist who decides which department handles your call.
↓
Step 3 — Router
🚦 Send to the right engine
Form / ID → AWS Textract Chart / Diagram → Llama Vision (self-hosted) Annual Report → Both
Textract is great at reading tables and forms. A self-hosted Llama 3.2 Vision model understands images and diagrams — run locally so KYC document contents never leave Eureka's infrastructure. Neither alone handles everything.
↓
Step 4 — Normalizer
🔧 Convert to one shared format
Both engines speak different languages. The normalizer translates both into one standard JSON — the canonical schema.
This is what Task 1 built. The schema. The "contract" every engine must follow.
↓
Step 5 — Graph DB
🕸️ Neo4j ingests the data
Entities become nodes. Relationships become edges. Now you can ask: "Who are the UBOs of this company?"

🗂️ What Is the Schema?

The most important thing we built. Everything else depends on it.

🔌 The Universal Plug Adapter Analogy

Imagine you're traveling across Asia. Your laptop charger doesn't fit every outlet. A universal adapter is the thing in the middle — your plug goes in one side, any country's outlet goes in the other. The schema is that adapter. Any engine goes in one side. The graph database always sees the same clean format on the other.

What the Schema Contains

🧑 Entity — "a thing we found"

This becomes a node in Neo4j. Examples:

👤
A person — name, aliases (Chinese name too!), HKID or passport number
🏢
A company — name, company registration number
📍
An address — where someone or something is registered
Each entity gets a confidence score — how sure was the engine? 0.99 = almost certain. 0.50 = a guess.

🔗 Relationship — "a connection between things"

This becomes an edge in Neo4j. Examples:

👑
UBO_OF — "Chan Tai Man owns 75% of Acme Holdings" → weight: 75.0
💼
DIRECTOR_OF — person sits on the board
⚠️
SANCTIONED_BY — entity is on OFAC / UN sanctions list
The evidence_span field stores the exact sentence from the document that proves this link. A compliance officer needs this for their STR report.

📎 Source Metadata

Where did this data come from? Which file, which page, when was it processed? This is your audit trail — regulators will ask.

🏷️ Provenance

When two engines both found the same entity, provenance records which one "won" and why. Hybrid documents need this.

Why Define the Schema FIRST?

❌ What happens if you don't

Textract returns: "BlockType": "KEY_VALUE", "Text": "Chan Tai Man"
VLM returns: "entity": "person", "label": "Chan Tai Man"

Now try merging them. They're completely different shapes. You'd need custom glue code for every pair of engines — and every time you add a new engine, you break everything.

✅ With the schema defined first

Both engines are required to produce an Entity(name="Chan Tai Man", confidence=0.95). The merger doesn't need to know anything about either engine. It just compares confidence scores and picks the winner. Adding a new engine = just write a normalizer for it. Nothing else changes.

👁️ How to Monitor AI

You don't need to read every line of code. You need to know
the right questions to ask and the right things to look at.

The 5 Questions to Ask Before Every Task

Question 1 — Scope
"What files are you creating or changing, and why?"
If AI says it's touching 10 files for a simple task, that's a red flag. Simple tasks should touch few files.
Question 2 — Contract
"What does this function take as input, and what does it return?"
This is the one thing you must understand about any piece of code — its interface. You don't need to understand the internals.
Question 3 — Failure
"What happens if this fails? How do I know it's broken?"
Good code fails loudly and obviously. Bad code fails silently and gives you wrong answers with no warning.
Question 4 — Evidence
"Show me the test or output that proves this works."
AI can write code that looks right but is wrong. A working test run is the only proof that counts.
Question 5 — Secrets
"Is any API key or credential hardcoded anywhere?"
This is a career-ending mistake. Keys must always live in .env files only, never in code.

What to Look At in the Output

After I run a task, here's your review checklist:

📁 File Review

✅
Does the list of files match what we planned?
✅
Are there any files you didn't expect?
✅
Is there a .env.example (not .env) in the repo?

🧪 Test Output

✅
Did the smoke test actually print output? (not just "no errors")
✅
Does the output make real-world sense? (e.g. a person entity has a name, not a number)
✅
Are confidence scores between 0.0 and 1.0? (not 99.1 — that's Textract's raw format, not ours)

🗂️ Schema Compliance

✅
Every entity has: entity_id, type, name, confidence
✅
Every relationship has: src, dst, kind, confidence
✅
engine_used is set — tells you which engine produced this result
✅
Hybrid results have provenance entries

Red Flags to Watch For

🚩
AI says "I'll handle that edge case later" Push back. "Later" means never. Edge cases in KYC are where data goes missing silently.
🚩
The output is valid JSON but the entities list is empty The code ran but extracted nothing. Something is wrong with the engine or the input parsing.
🚩
Confidence is always 1.0 on everything That means confidence isn't actually being calculated — it's just the default. Real extraction is never 100% confident.
🚩
No provenance on a hybrid document If both engines ran but provenance is empty, the merger isn't recording which engine produced what.
🚩
An API key appears in any .py file Stop immediately. This is a security issue. Keys belong only in .env.

🔧 How to Debug

You don't need to fix the code yourself. You need to describe the problem clearly
so AI can fix it fast.

🏥 The Doctor Analogy

A doctor doesn't need to perform surgery to diagnose a problem. They ask the right questions, look at the right signals, and tell the surgeon exactly where to cut. Debugging is the same — your job is diagnosis, not surgery.

The 3-Step Debug Method

Step 1 — What did you expect vs. what did you get?

Example: "I expected the entity list to have 2 entries. It has 0."
Or: "I expected confidence to be between 0 and 1. It's showing 99.1."

This one sentence tells me everything I need to know to find the bug.

Step 2 — Where in the pipeline did it break?

Use the 4-stage pipeline as your map:

🔍
Did the classifier return the wrong document type?
🚦
Did the router send it to the wrong engine?
⚙️
Did the engine return garbage or nothing?
🔧
Did the normalizer map the fields incorrectly?

You don't need to read the code to answer this — just look at what each stage returns.

Step 3 — Give me the exact error message

Copy the full error text — don't summarize it. Error messages are written for machines, and the exact wording matters. Paste it and say: "Here's what I got, here's what I expected."

Good vs. Bad Bug Reports

❌ Bad bug report

"It's not working."

This tells me nothing. I have to guess what "not working" means, which wastes time.

✅ Good bug report

"I ran the smoke test. The ExtractionResult printed, but entities is an empty list. I gave it a form with two names visible. I expected at least 2 entity entries."

Questions to Ask Me at Each Task

At the start of every task
"Show me the plan before you write any code. What files, what functions, what inputs and outputs?"
After the code is written
"Run the test and show me the actual output — not just 'it passed.'"
When results look wrong
"The confidence is always 1.0. Is that real or is it the default? Show me where it's being calculated."
Before moving to next task
"What assumptions did you make that I should know about? What could break later?"

🎯 Learning Checkpoint

Answer these 4 questions in your own words.
Think "how would I explain this to the CEO?"

Why answer in your own words?

The founder is a 20-year banking veteran. In your first meeting with him, he will ask you to explain your system in plain English — not show him code. These questions are practice for that conversation.

Question 1 — The Schema
Why did we define the data format (the "schema") before writing any of the actual extraction engines?
Hint: what would happen to the merger step if Textract and the Llama Vision engine returned data in completely different shapes?
Question 2 — Two Confidence Scores
The final result has one overall confidence score AND every single entity has its own confidence score. Why two levels? Give a real example where they'd be different numbers.
Hint: imagine a hybrid annual report where the table of shareholders was perfectly clear but the hand-drawn org chart was smudged.
Question 3 — The Identifiers Dict
Person entities store IDs as a flexible dictionary like {"hkid": "A123456", "passport": "HK999"} instead of fixed fields. Why is that a smarter design for a KYC company operating across Asia?
Hint: Hong Kong uses HKIDs. Singapore uses NRICs. Mainland China uses resident IDs. How many fixed fields would you need?
Question 4 — Evidence Span
Every relationship stores the raw sentence that proves it (the "evidence span"). As a compliance officer writing a Suspicious Transaction Report (STR), why would you specifically need this field?
Hint: a regulator asks you: "How do you know Chan Tai Man owns 75% of Acme Holdings?" What do you show them?
